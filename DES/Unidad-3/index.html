Unidad 3. Servidores de aplicaciones. Despliegue de aplicaciones web

Esta unidad tiene 5 actividades guiadas paso a paso: despliegas la misma idea con Node.js, Flask, Docker, WildFly y Django. Ver las actividades

1. Introducción

Un servidor de aplicaciones es un conjunto de software que permite tanto crear aplicaciones web como ofrecer el entorno de servidor donde se ejecutan.

A menudo es una pila de elementos que hacen tareas concretas y que tienen que trabajar como uno solo para dar servicio a aplicaciones web y en la nube.

Está situado entre el servidor web y el servidor de bases de datos. Hace de intermediario entre la base de datos y los usuarios de las aplicaciones, y para ello usa distintos protocolos e interfaces de programación de aplicaciones (API).

Es habitual que se use junto con un servidor web o que lleve uno integrado, por lo que a veces se habla de servidor de aplicaciones web. También puede trabajar a la vez con otros servidores de aplicaciones.

Los servidores de aplicaciones pueden tener su propia interfaz gráfica de administración y se ocupan de sus propios recursos: procesamiento de transacciones, mensajería, agrupación de recursos y conexiones, y tareas de seguridad.

2. El servidor de aplicaciones

Las aplicaciones tienen todo tipo de formas, tamaños y usos. Los servidores de aplicaciones son los equipos que proporcionan los recursos de esas aplicaciones a los usuarios y a los clientes web.

Se sitúan, física o virtualmente, entre los servidores de bases de datos que guardan los datos de las aplicaciones y los servidores web que se comunican con los clientes. Junto con el middleware, son la base sobre la que se desarrolla y se entrega una aplicación, sea de escritorio, móvil o web.

2.1. Terminología

Término Descripción
Servidor web Guarda, procesa y entrega las páginas web.
Cliente web El extremo que intenta acceder a los recursos de la web o de la aplicación (por ejemplo, un navegador).
HTTPS Protocolo de comunicación seguro entre el servidor web y los clientes web.
JSON Formato de datos para el intercambio entre los servidores web y de aplicaciones.
Lógica de negocio Reglas para guardar los datos y transferir los recursos de la aplicación.
Aplicación Un programa o un sitio web unido a una base de datos.

2.2. Su papel en la arquitectura de servicios

Cuando los usuarios o los clientes web piden acceso a una aplicación, el servidor de aplicaciones suele hacer el trabajo pesado en el backend: guarda y procesa las peticiones dinámicas de la aplicación.

2.3. ¿Por qué necesitamos servidores de aplicaciones?

Miles de millones de clientes web hacen peticiones HTTP cada día y esperan una respuesta inmediata. Da igual la aplicación (Google Docs para un informe, una red social en el descanso…): se consulta en un servidor de aplicaciones y se devuelve a través de un servidor web.

Los servidores web responden a las peticiones HTTP de los clientes con respuestas HTTP. A diferencia de los servidores de aplicaciones, son lo bastante ligeros como para servir el contenido estático de varias aplicaciones o sitios web manteniendo la seguridad. Las peticiones dinámicas, típicas de las aplicaciones, necesitan ayuda adicional.

2.4. Optimizan el tráfico y añaden seguridad

Para que el servidor web sea ágil, no conviene que además de atender las peticiones HTTP tenga que procesar o guardar los recursos de varios sitios. Los servidores de aplicaciones cubren ese hueco: están pensados para atender las peticiones de contenido dinámico.

También aportan redundancia y una capa más de seguridad. Al estar entre la base de datos y el servidor web, es más fácil replicar la aplicación en la red, y hay un paso más entre las posibles peticiones maliciosas y los datos de la base de datos. Como el servidor de aplicaciones procesa la lógica de negocio, un intento de inyección SQL también es más difícil.

Las organizaciones pueden proteger aún más sus datos con un servidor proxy inverso delante. Los proxies y las VPN ayudan a ocultar y cifrar la comunicación para proteger a los usuarios y los datos de la empresa.

2.5. Los servidores de aplicaciones hoy

Las previsiones publicadas en 2020 daban al mercado de los servidores de aplicaciones un crecimiento anual del 13,2 %: de unos 17.000 millones de dólares en 2020 a 41.000 millones en 2026. No es una sorpresa, porque la conexión a Internet y la dependencia de las aplicaciones no paran de crecer.

La migración a la nube y el auge de los dispositivos IoT son dos de los motores de este mercado. A esto se suman las políticas BYOD (Bring Your Own Device, cada persona trabaja con su propio dispositivo) y el teletrabajo, que necesitan más conectividad y eficiencia.

Los servidores de aplicaciones son el mejor aliado del servidor web: cuando una petición es demasiado para el servidor web, el servidor de aplicaciones permite seguir atendiendo el contenido dinámico sin problemas. Sin una conexión estable y escalable a las aplicaciones, los clientes se van.

3. Cómo funciona un servidor de aplicaciones

Vamos a verlo con el ejemplo de un servidor de aplicaciones Java.

3.1. Los servlets

Un servlet es un programa Java que se ejecuta en el servidor y construye o sirve páginas web. Así se crean páginas dinámicas a partir de datos variables: lo que escribe el usuario, fuentes de información que cambian (como una página de noticias) o programas que sacan información de bases de datos.

Comparado con un CGI, un servlet es más sencillo de usar, más eficiente (arranca un hilo por cada petición y no un proceso entero), más potente y portable. Con los servlets se pueden procesar, sincronizar y coordinar muchas peticiones de clientes, o reenviarlas a otros servlets o a otros servidores.

Como la mayoría de los servidores actuales, los servidores de aplicaciones incluyen seguridad, transacciones, servicios, clustering, diagnóstico y bases de datos. Lo que los distingue es que pueden procesar las peticiones de servlets (programas Java) que les llegan desde un servidor web.

3.2. El recorrido de una petición

  1. El cliente abre un navegador y pide acceso a un sitio web.
  2. El servidor web recibe la petición HTTP y responde con la página pedida.
  3. El servidor web atiende las peticiones de datos estáticos, pero el cliente quiere usar una herramienta interactiva.
  4. Como es una petición de datos dinámicos, el servidor web la pasa al servidor de aplicaciones.
  5. El servidor de aplicaciones recibe la petición HTTP y la convierte en una petición de servlet.
  6. El servlet consulta el servidor de base de datos y el servidor de aplicaciones recibe la respuesta del servlet.
  7. El servidor de aplicaciones traduce la respuesta del servlet a HTTP para que llegue al cliente.

Como los servidores de aplicaciones trabajan sobre todo con la lógica de negocio, el servidor web se encarga de pasar al usuario una respuesta HTTP que pueda entender.

3.3. Servidor de aplicaciones y servidor web

Característica Servidor de aplicaciones Servidor web
Diseñado para Atender peticiones HTTP y de lógica de negocio Atender peticiones HTTP
Guarda y proporciona Lógica de negocio Contenido web estático
Uso de recursos Pesado Ligero
Soporta Transacciones distribuidas y Enterprise JavaBeans (EJB) Servlets, Java Server Pages (JSP) y JSON

En el mundo Java, a un servidor web que solo ejecuta servlets y JSP (como Apache Tomcat) se le llama contenedor web o contenedor de servlets. Un servidor de aplicaciones completo, como WildFly, añade el resto de especificaciones (EJB, transacciones, mensajería…).

4. El despliegue de aplicaciones web

En el desarrollo de software y web, desplegar es pasar los cambios o actualizaciones de un entorno a otro. Cuando montas un sitio web, siempre tienes el sitio en vivo: el entorno de producción.

4.1. Entornos de despliegue

Si quieres hacer cambios sin afectar al sitio en producción, puedes (y debes) añadir más entornos: los entornos de desarrollo o de despliegue. Lo habitual es tener un entorno local, uno de desarrollo y uno de preproducción (staging). Cuántos hacen falta depende del proyecto y de su complejidad.

El modelo más común es el clásico «de izquierda a derecha»: los cambios se hacen en los entornos local, de desarrollo o de preproducción y van pasando de izquierda a derecha por los distintos entornos hasta llegar a producción. Al terminar el despliegue, los cambios se ven en el sitio en vivo.

No siempre hacen falta todos los entornos, pero el proceso es el mismo. La gran ventaja de tener varios es que puedes hacer cambios sin que afecten al sitio en vivo: cuando están hechos, probados y listos, el proceso de despliegue se encarga del resto.

4.2. El plan de despliegue

Para que el proceso vaya lo más fluido posible, es fundamental tener un plan de despliegue. El plan garantiza que todo se haga siempre de la misma manera y reduce los conflictos y errores, sobre todo cuando varias personas trabajan en el mismo proyecto.

Un buen plan incluye horarios, reglas sobre cuándo pasar los cambios de un entorno a otro (desarrollo, preproducción, producción) y qué hacer si hay errores o hay que deshacer los cambios.

El flujo que se describe a continuación es una simplificación con lo fundamental. No es la única forma de hacerlo, pero es una buena base para entender las partes más importantes.

4.3. Las cinco fases del despliegue

  1. Planificación. Además del plan general, hay que planificar cada cambio. Para un cambio pequeño será rápido; para uno grande, mucho más detallado. Cuanto antes se planifique, más fácil será el despliegue.
  2. Desarrollo. Con el plan en marcha, se hace el desarrollo. Para que varias personas puedan trabajar a la vez sin romper nada, se trabaja solo en entornos locales o de desarrollo. Al terminar, se empiezan a probar y desplegar los cambios por los distintos entornos.
  3. Pruebas. Probar es clave para que no lleguen errores a producción. Cuando todo funciona en local, se despliega al siguiente entorno (preproducción o staging), que debe ser lo más parecido posible al real. Ahí se hacen las pruebas finales de control de calidad (QA). Si aparecen errores, los cambios vuelven a desarrollo y se repite el ciclo de pruebas.
  4. Despliegue en producción. Con todo probado y corregido, se despliega en el entorno real. Debería ser un paso seguro gracias a las fases anteriores, pero siempre puede fallar algo; por eso el proceso no acaba aquí.
  5. Supervisión. Con los cambios en marcha y los usuarios usándolos, hay que vigilar que todo funcione como estaba previsto: los usuarios pueden encontrar problemas o hacer cosas que no se habían pensado. Conviene desplegar en momentos de poco tráfico y tener al equipo preparado para arreglar o deshacer los cambios. Si hay que deshacerlos, hazlo con la misma calma y el mismo cuidado que el despliegue.

4.4. Tipos de despliegue

Lo que se despliega se suele dividir en dos partes, porque afectan de forma distinta al nuevo entorno:

  • Metadatos: cambios en el código, las plantillas, las hojas de estilo, los archivos… Suelen necesitar una comprobación entre entornos para ver si hay algún conflicto. Muchas herramientas de despliegue incluyen comprobaciones de coherencia y te guían si hay conflictos.
  • Contenido: textos, imágenes y vídeos. Se tratan de otra forma; por eso muchas herramientas permiten que también lo desplieguen los editores de contenido, no solo los desarrolladores.

4.5. Buenas prácticas

  • Usa Git. Un sistema de control de versiones es imprescindible. Sin él es fácil cometer errores en equipo, e incluso si trabajas solo te permite volver a versiones anteriores o incorporar a alguien nuevo.
  • Trabaja en ramas. Cada funcionalidad en su rama, para trabajar en varias a la vez sin que se afecten y con la rama principal (main) siempre estable.
  • Usa un entorno local. Se puede trabajar directamente en un servidor de desarrollo, pero en local ahorras mucho tiempo y las pruebas son más rápidas.
  • Revisa las diferencias antes del despliegue final. Antes de pasar a producción, revisa las diferencias (diff) entre lo que está en producción y lo que vas a desplegar.
  • Usa grupos de usuarios con distintos permisos. Cualquier desarrollador debe poder llevar cambios a los entornos de prueba, pero conviene limitar quién puede desplegar en producción.

4.6. Si algo se rompe, calma

Acabas de desplegar en producción y la web está rota. ¿Y ahora qué?

Por desgracia, estas cosas pasan. En lugar de entrar en pánico y aplicar parches (hotfixes) o volver atrás sin pensar, mantén la calma. Primero comprueba si se puede volver a la versión anterior (rollback) y si de verdad arreglaría algo: a veces un rollback causa problemas aún mayores.

Ten un plan preparado y respira hondo antes de buscar la solución. Parece una tontería, pero ayuda a salir antes de una mala situación.

4.7. ¿A qué hora conviene desplegar?

Para que un posible error afecte lo menos posible, hazte dos preguntas:

  • ¿Cuándo hay menos usuarios activos? Normalmente se busca el momento del día con menos usuarios usando la web o el programa.
  • ¿Habrá alguien preparado para vigilar y arreglar problemas después? Si la respuesta es no, desplegar en mitad de la noche puede no ser buena idea.

No hay un momento perfecto, pero sí momentos mejores que otros.

4.8. Ventajas de usar varios entornos

  • Menos riesgo: es la razón principal; los cambios no afectan directamente al sitio en vivo.
  • Ahorro de tiempo: sin miedo a romper el sitio en vivo, los desarrolladores trabajan más ágiles.
  • Contenido con fecha: si hay campañas que solo pueden salir un día o a una hora concretos, tenerlas preparadas en otro entorno ahorra mucho estrés.

5. Despliegue de aplicaciones Java

En el lado del servidor necesitamos que el servidor HTTP pueda ejecutar aplicaciones que recojan las peticiones del cliente, las procesen y devuelvan un documento dinámico. Normalmente son programas que consultan bases de datos, procesan la información y devuelven el resultado al servidor.

Nos centramos en las aplicaciones web Jakarta EE (antes Java EE), en las que los componentes dinámicos (servlets y JSP) reciben las peticiones HTTP y usan otros componentes Java (Beans, EJB) para hacer lo necesario.

Jakarta EE es un conjunto de especificaciones para aplicaciones empresariales en Java. WildFly (antes JBoss) es un servidor de aplicaciones potente y flexible que las implementa.

En 2019 Java EE pasó a llamarse Jakarta EE. Desde Jakarta EE 9 los paquetes cambiaron de nombre: javax.servlet ahora es jakarta.servlet. Los servidores actuales (como WildFly 27 o posteriores) solo entienden jakarta.*, así que el código antiguo con javax.* hay que adaptarlo.

5.1. Estructura de una aplicación web Java

Una aplicación web Jakarta EE tiene una estructura de carpetas fija:

  • En la carpeta raíz de la aplicación van las páginas HTML o JSP.
  • Dentro de la raíz tiene que haber una carpeta WEB-INF con la información web de la aplicación (por ejemplo, el descriptor web.xml).
  • El resto de elementos (imágenes, etc.) se organizan como convenga.

5.2. Empaquetado: archivos WAR

Una forma de distribuir aplicaciones web es empaquetarlas enteras en un archivo WAR (Web Application Archive). Es un estándar de Jakarta EE, así que sirve en los distintos servidores de aplicaciones. Para desplegarlo, la mayoría de servidores permiten hacerlo desde una consola de administración o simplemente copiando el WAR en una carpeta concreta.

5.3. Maven: gestión de proyectos Java

Maven es una herramienta libre que simplifica la construcción (build: compilar y generar el ejecutable) y gestiona un proyecto completo, desde la compilación hasta el despliegue.

Maven define tres ciclos de construcción con una serie de fases. El ciclo por defecto tiene estas:

Fase (comando) Qué hace
validate Comprueba que el proyecto es correcto.
compile Compila el código fuente.
test Prueba el código compilado con un framework de pruebas unitarias.
package Empaqueta el código en un formato distribuible, como .jar o .war.
integration-test Despliega el paquete en un entorno para las pruebas de integración.
verify Comprueba que el paquete es válido y cumple los criterios de calidad.
install Instala el paquete en el repositorio local de Maven para usarlo como dependencia.
deploy Copia el paquete final a un repositorio remoto para compartirlo.

Maven gestiona además las dependencias del proyecto con un archivo de configuración llamado pom.xml (Project Object Model).

6. Despliegue de aplicaciones Node.js con Express

6.1. ¿Qué es Node.js?

Node.js es un entorno de ejecución de JavaScript del lado del servidor. No es un lenguaje ni un framework: es lo que permite ejecutar JavaScript fuera del navegador. Es rápido y eficiente con muchas conexiones a la vez. Por sí solo no sabe servir archivos ni gestionar rutas cómodamente, así que se usa con un framework como Express.

6.2. ¿Qué es Express?

Express es un framework minimalista y flexible de Node.js para crear aplicaciones web y API de forma rápida y sencilla. Simplifica tareas comunes como gestionar rutas, peticiones HTTP y respuestas.

A diferencia de Apache o Nginx, en Node.js la aplicación es el servidor. No despliegas la aplicación sobre un servidor web: la aplicación lleva el servidor web dentro. Por eso en producción se suele poner Nginx delante como proxy inverso.

6.3. ¿Qué es npm?

npm (Node Package Manager) es el gestor de paquetes de JavaScript. Tiene un repositorio en línea de paquetes y una herramienta de línea de comandos para instalarlos y gestionar las dependencias de un proyecto, igual que apt en Debian pero para paquetes de JavaScript.

6.4. El archivo package.json y los scripts de npm

Cada proyecto Node.js tiene un archivo package.json que describe el proyecto y sus dependencias. Con la propiedad scripts puedes definir comandos para automatizar tareas como compilar, probar o desplegar, y lanzarlos con npm run nombre:

{
  "scripts": {
    "build": "tsc",
    "format": "prettier --write **/*.ts",
    "lint": "eslint src/**/*.ts",
    "test": "jest",
    "all": "npm run build && npm run format && npm run lint && npm test"
  }
}

7. Despliegue de aplicaciones Python

Python es un lenguaje de programación de alto nivel, fácil de leer y escribir. Es muy usado en desarrollo web, ciencia de datos, inteligencia artificial y automatización, y suele venir instalado en Debian.

7.1. pip y los entornos virtuales

  • pip es el gestor de paquetes de Python, equivalente a npm en Node.js o a apt en Debian.
  • Un entorno virtual (python3 -m venv) es un espacio aislado donde instalar paquetes de Python sin tocar el sistema. Lo correcto es usar uno por proyecto. En Debian, además, pip no deja instalar paquetes fuera de un entorno virtual.
  • El archivo requirements.txt guarda la lista de dependencias con sus versiones, para recrear el entorno en otro servidor (pip install -r requirements.txt).

7.2. Flask y Django

Flask es un micro-framework web para Python. Se llama «micro» porque su núcleo es sencillo, pero se puede ampliar con extensiones. Sirve desde para una API pequeña hasta para una aplicación web completa.

Django es un framework web libre de alto nivel que sigue el patrón Modelo-Vista-Plantilla (MVT) y el principio de «pilas incluidas»: trae ORM, autenticación, panel de administración y mucho más. Lo usan sitios como Instagram, Pinterest o Mozilla.

Mientras que Flask te da lo mínimo y tú eliges las herramientas, Django es un framework completo con todo integrado.

7.3. WSGI y Gunicorn

El servidor que traen Flask (flask run o python app.py) y Django (runserver) es solo para desarrollo. En producción se usa un servidor WSGI (Web Server Gateway Interface, la interfaz estándar entre servidores web y aplicaciones Python) como Gunicorn, que se ejecuta como servicio de systemd y se pone detrás de Nginx:

Usuario → Nginx (puerto 80) → Gunicorn → aplicación Flask o Django

8. Contenedores: Docker

Docker permite empaquetar una aplicación con todas sus dependencias (Node.js, librerías, configuración) en una unidad estándar llamada contenedor. ¿Por qué usarlo?

  • Consistencia: se acabó el «en mi máquina funciona». Si funciona en Docker, funciona en cualquier sitio.
  • Aislamiento: cada aplicación tiene su propio entorno, sin conflictos de versiones con las demás.
  • Portabilidad: el mismo contenedor pasa fácilmente de desarrollo a producción.

Una imagen es la «receta» ya construida (se crea con un Dockerfile o se descarga de Docker Hub) y un contenedor es una imagen en marcha. Para aplicaciones con varias piezas (por ejemplo, WordPress y su base de datos) se usa Docker Compose, que las describe todas en un archivo docker-compose.yml y las arranca con docker compose up.

9. CI/CD: integración y despliegue continuos

La CI/CD es una forma de entregar aplicaciones a los clientes con frecuencia gracias a la automatización. Los conceptos clave son la integración, la entrega y el despliegue continuos.

  • Integración continua (CI): los cambios en el código se integran y se prueban automáticamente y con frecuencia en un repositorio compartido, para evitar problemas de integración.
  • Entrega continua (CD, Continuous Delivery): es el paso siguiente. El código que pasa la CI se empaqueta y se deja listo automáticamente para producción. El despliegue final suele ser un paso manual.
  • Despliegue continuo (CD, Continuous Deployment): va un paso más allá. Cada cambio que supera todas las etapas anteriores se despliega solo en producción, sin intervención humana.
