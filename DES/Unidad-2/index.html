Introducción

Con la llegada de Internet y su acceso libre, uno de sus grandes atractivos ha sido la publicación de páginas web: contenidos que se guardan en un sitio y que cualquiera puede consultar desde cualquier parte del mundo.

Con la popularización de Internet, tanto las empresas como los particulares han necesitado un sitio desde el que anunciar sus productos o, a título personal, dar a conocer sus aficiones o sus capacidades publicando páginas web.

Las páginas web, en su mayoría en formato HTML, tienen que alojarse en máquinas con espacio en disco para guardar los archivos HTML, las imágenes, el código o los vídeos en directorios concretos. Además, estas máquinas tienen que saber tratar todo tipo de archivos que se envían en los dos sentidos de la comunicación.

Al mismo tiempo, no se puede olvidar la seguridad frente a los peligros de Internet. Por eso las páginas deben usar protocolos de comunicación seguros, como el protocolo seguro de transferencia de hipertexto (HTTPS).

Las máquinas que alojan las páginas web se llaman servidores web. Sus requisitos más importantes son el espacio en disco para guardar la estructura de la web y una buena conexión de red; el consumo de procesador (CPU) suele ser bajo.

Los servidores web tienen un consumo de recursos especial, en forma de diente de sierra: pueden pasar un rato sin peticiones y, de repente, recibir una avalancha. Por eso suelen tener pocos procesos en espera y van arrancando más a medida que hacen falta.

1. ¿Qué es un servidor web?

Los servidores web guardan contenidos de Internet y los tienen disponibles de forma constante y segura. Cuando visitas una página web desde tu navegador, es un servidor web el que envía a tu ordenador cada una de las partes de esa página. Por eso, para que una web esté accesible en cualquier momento, su servidor tiene que estar siempre en línea.

Toda página accesible en Internet necesita un servidor para sus contenidos. Las grandes empresas y organizaciones suelen tener servidores propios, pero la mayoría de los administradores contratan los centros de datos de proveedores de alojamiento web.

1.1. Tecnología de servidores web

El software del servidor HTTP es el que entrega los datos para que se vea el contenido web.

Para abrir una página web, el usuario solo tiene que escribir su URL en el navegador. El navegador envía una petición al servidor web, y este responde con una página HTML. Esa página puede ser un documento estático o generarse de forma dinámica: en ese caso, el servidor ejecuta un código (por ejemplo, PHP) antes de responder.

El navegador interpreta la respuesta y, normalmente, eso provoca más peticiones para conseguir otros recursos, como imágenes o archivos CSS.

El protocolo que se usa es HTTP (o su variante cifrada, HTTPS), que funciona sobre los protocolos de red IP y TCP. Un servidor web puede entregar contenidos a varios ordenadores a la vez. Cuántas peticiones atiende y a qué velocidad depende del hardware, de la carga del equipo y de lo complejo que sea el contenido.

Al elegir el servidor, y decidir si debe ser dedicado, virtual o en la nube, hay que pensar siempre en evitar que se sobrecargue. Aunque encuentres un servidor que se adapte perfectamente a tu proyecto, siempre puede fallar por problemas técnicos o por cortes de luz en el centro de datos. No es muy frecuente, pero durante ese tiempo sin servicio (downtime) la web no estará disponible.

1.2. Otras funciones de los servidores web

Aunque su función principal es enviar contenido web, los servidores web ofrecen más cosas:

Función Descripción
Seguridad Cifrado de la comunicación entre el servidor y el cliente con HTTPS.
Autenticación Autenticación HTTP para proteger partes concretas de una aplicación web.
Redirección Redirección de peticiones con un motor de reescritura (rewrite engine).
Caché Guardar respuestas para mejorar el rendimiento y evitar sobrecargas.
Cookies Envío y tratamiento de cookies HTTP para gestionar sesiones.

Además del servidor web, una máquina puede tener otros programas: por ejemplo, un servidor FTP o SFTP para subir archivos o un servidor de bases de datos para los contenidos dinámicos. En general hay muchos tipos de servidores para distintos fines: servidores de correo, de juegos, proxy…

2. El protocolo HTTP

2.1. Historia: el origen en el CERN

El protocolo de transferencia de hipertexto (HTTP, Hypertext Transfer Protocol) es el motor de la World Wide Web (WWW).

La web nació en 1989 en el CERN (Organización Europea para la Investigación Nuclear), en Ginebra. Allí trabajan científicos de muchos países, en equipos de distintas nacionalidades, y sus experimentos necesitan años de planificación y colaboración.

Para que grupos de científicos repartidos por el mundo pudieran colaborar bien, enviándose informes, dibujos, esquemas, fotos y todo tipo de documentos enlazados y accesibles, el científico británico Tim Berners-Lee propuso un sistema de gestión de la información que acabaría convirtiéndose en la web.

La primera versión del protocolo, la 0.9, es de principios de los años noventa. Era muy sencilla y solo servía para transferir páginas web escritas en HTML. A partir de la versión 1.0 se pudieron enviar mensajes con cabeceras (headers) que describían su contenido, lo que abrió la puerta a contenidos mucho más ricos y variados.

2.2. HTTP/1.0 y HTTP/1.1: la estandarización de la web

HTTP/1.0 se publicó formalmente en 1996. Estandarizó el uso de cabeceras para que el cliente y el servidor pudieran intercambiar metadatos, y así enviar distintos tipos de contenido, no solo HTML. Pero tenía una gran limitación: abría una conexión TCP nueva para cada recurso (cada imagen, cada archivo CSS…), y eso era muy poco eficiente.

Para resolverlo, en 1997 se publicó HTTP/1.1, la versión que fue el estándar de Internet durante casi dos décadas. Aclaró ambigüedades y añadió mejoras muy importantes:

  • Conexiones persistentes (keep-alive): una misma conexión TCP se puede reutilizar para varias peticiones, y se ahorra el tiempo y los recursos de abrirla cada vez.
  • Pipelining: permite enviar una segunda petición antes de que llegue la respuesta de la primera. En teoría reducía la espera, pero en la práctica dio muchos problemas y muchos proxies y servidores no lo soportaban bien, así que no fue la solución definitiva.
  • Respuestas por partes (chunked transfer): la respuesta se puede dividir en trozos, y así se puede enviar contenido sin saber de antemano su tamaño total.
  • Negociación de contenido: cabeceras como Accept-Language o Accept-Encoding permiten que el cliente y el servidor acuerden el contenido más adecuado (por ejemplo, la versión en español o en inglés, comprimido o sin comprimir).
  • Cabecera Host: una de las novedades más importantes, porque permite alojar varios dominios (varios sitios web) en la misma dirección IP. Sin ella no existiría el alojamiento compartido (virtual hosting) tal y como lo conocemos.

2.3. HTTP/2: más rendimiento

Con los años, las páginas web se volvieron cada vez más complejas. Para cargar una web moderna, el navegador tiene que pedir muchos megabytes de datos y hacer, a veces, más de cien peticiones HTTP. HTTP/1.1 atiende las peticiones de una conexión de una en una, lo que crea un cuello de botella llamado bloqueo de cabeza de línea (Head-of-Line Blocking, HOL). Por eso las páginas complejas cargaban despacio.

Google desarrolló un protocolo experimental, SPDY (se pronuncia speedy), que sirvió de base para el estándar oficial HTTP/2, publicado en 2015. Su objetivo era acelerar la carga de las páginas sin cambiar la semántica de HTTP: los métodos, los códigos de estado y las cabeceras siguen siendo los mismos.

Sus mejoras principales son:

  • Multiplexación: la característica estrella. Permite enviar varias peticiones y respuestas a la vez, y en cualquier orden, por una única conexión TCP. Así desaparece el bloqueo de cabeza de línea a nivel de HTTP.
  • Compresión de cabeceras (HPACK): las cabeceras, que se repiten mucho de una petición a otra, se comprimen para enviar menos datos.
  • Flujos (streams) con prioridad: el cliente puede indicar qué recursos son más importantes (por ejemplo, el CSS antes que las imágenes del pie de página) para que se envíen antes.
  • Server Push: el servidor podía enviar recursos antes de que el cliente los pidiera (por ejemplo, el CSS junto con el HTML). En la práctica apenas se usó y los navegadores actuales ya no lo admiten.

HTTP/2 se extendió muy rápido: lo usan la mayoría de los sitios web importantes y lo soportan todos los navegadores modernos.

2.4. HTTP/3: HTTP sobre QUIC

Un punto débil de HTTP/1.1 y HTTP/2 es que funcionan sobre TCP. TCP garantiza que los paquetes llegan en orden, pero si se pierde uno por el camino, todo el flujo se detiene hasta que se vuelve a enviar. Esto provoca otra vez un bloqueo de cabeza de línea, pero ahora a nivel de TCP, que afecta a todas las peticiones de esa conexión.

Para resolverlo, HTTP/3 (estandarizado en 2022) no funciona sobre TCP, sino sobre un protocolo de transporte nuevo, QUIC, que a su vez va sobre UDP. QUIC vuelve a implementar las garantías de TCP (como reenviar los paquetes perdidos), pero lo hace por separado en cada flujo. Así, si se pierde un paquete de un recurso (por ejemplo, una imagen grande), solo se detiene ese recurso: el CSS, el texto y los demás siguen llegando sin interrupciones. Hoy lo soportan todos los navegadores modernos.

2.5. Funcionamiento: un diálogo cliente-servidor

HTTP funciona de forma bastante sencilla: un cliente (normalmente un navegador) y un servidor (donde está alojada la web) se envían mensajes de texto. Es como un diálogo con unas reglas muy claras.

El proceso de comunicación se puede dividir en estos pasos:

  1. El usuario inicia la petición. Todo empieza cuando el usuario accede a una URL: pulsando un enlace, escribiéndola en la barra de direcciones o con cualquier otra acción en una aplicación web.
  2. El navegador descompone la URL y resuelve el dominio (DNS). El navegador separa las partes de la URL:
    • Protocolo o esquema: http:// o https://
    • Dominio o host: www.miweb.com
    • Puerto (opcional): :80 (el de HTTP) o :443 (el de HTTPS). Si no se escribe, se usa el puerto por defecto.
    • Ruta del recurso (path): /documento.html
    Antes de hablar con el servidor, el navegador necesita su dirección IP. Para ello hace una consulta DNS (Domain Name System), que traduce el nombre de dominio (www.miweb.com) a su IP (por ejemplo, 203.0.113.10).
  3. Se establece una conexión TCP/IP. Con la IP, el navegador abre una conexión TCP con el servidor. Este proceso, el saludo de tres vías (three-way handshake), asegura que los dos extremos están listos para comunicarse de forma fiable. La conexión se hace en el puerto correspondiente: normalmente el 80 para HTTP o el 443 para HTTPS (en ese caso, además, se negocia el cifrado TLS antes de enviar nada).
  4. El cliente envía la petición HTTP. Por esa conexión, el navegador envía un mensaje de petición con una estructura concreta:
    • Línea de inicio: el método (GET, POST…), la ruta del recurso (/documento.html) y la versión del protocolo (HTTP/1.1). Por ejemplo: GET /documento.html HTTP/1.1.
    • Cabeceras: líneas con información adicional, como el dominio al que va la petición (Host: www.miweb.com), el navegador (User-Agent) o los formatos que acepta (Accept).
    • Cuerpo: un bloque de datos opcional. Está vacío en las peticiones GET; en las POST lleva los datos que se envían (por ejemplo, los de un formulario).
  5. El servidor procesa la petición y devuelve una respuesta HTTP. El servidor busca el recurso (o ejecuta la lógica necesaria) y responde con un mensaje que también tiene una estructura fija:
    • Línea de estado: la versión del protocolo, un código de estado que indica el resultado (por ejemplo, 200 OK si todo ha ido bien o 404 Not Found si no encuentra el recurso) y un texto descriptivo. Por ejemplo: HTTP/1.1 200 OK.
    • Cabeceras: información sobre la respuesta, como el tipo de contenido (Content-Type: text/html), su tamaño (Content-Length) o datos de caché.
    • Cuerpo: el recurso pedido (el HTML, la imagen, el JSON…).
  6. El navegador muestra la respuesta y gestiona la conexión. El navegador interpreta la respuesta (si es HTML, empieza a construir el DOM) y se la muestra al usuario. Lo que pasa con la conexión TCP depende de la versión:
    • En HTTP/1.0, la conexión se cerraba después de cada respuesta.
    • En HTTP/1.1, la conexión se mantiene abierta (keep-alive) para pedir más recursos (imágenes, CSS…) sin repetir el costoso proceso de abrirla.
    • En HTTP/2, una única conexión sirve para descargar varios recursos a la vez (multiplexación).

    Por ejemplo, si un documento HTML tiene dentro 2 imágenes y 1 vídeo, el ciclo de petición y respuesta se repite para cada uno de esos recursos, a ser posible por la misma conexión TCP.

3. Métodos HTTP: los verbos de la web

HTTP define un conjunto de métodos de petición que indican qué acción se quiere hacer sobre un recurso. Se les llama «verbos HTTP» porque describen la intención del cliente.

3.1. Métodos principales (operaciones CRUD)

Son los más usados y se corresponden con las operaciones CRUD (Create, Read, Update, Delete: crear, leer, actualizar y borrar) de las bases de datos.

Método Para qué sirve CRUD Idempotente Cuerpo
GET Pedir y obtener un recurso del servidor. Se usa cada vez que pulsas un enlace o escribes una URL en el navegador. Read (leer) Sí: repetir la misma petición da el mismo resultado. No. Los datos van en la propia URL (query string).
POST Enviar datos al servidor para que los procese; normalmente crea un recurso nuevo. Es el método de los formularios: el servidor pasa los datos a un proceso que los trata (por ejemplo, insertar una fila en una base de datos). Create (crear) No: repetirla puede crear varios recursos. Sí, con los datos que se envían.
PUT Enviar datos para actualizar un recurso existente en una URL concreta, o crearlo si no existe. La petición lleva el recurso completo. Update (actualizar) Sí: enviarla 10 veces deja el recurso igual que enviarla una. Sí, con el recurso completo.
DELETE Borrar el recurso de una URL. Muchos servidores lo restringen y piden autenticación y autorización. Delete (borrar) Sí: borrar algo ya borrado no cambia nada. Puede tenerlo, pero no es habitual.
POST o PUT, una confusión muy habitual:
  • Usa POST cuando no sabes cuál será la URL del recurso que vas a crear. Por ejemplo, para crear un usuario envías los datos a /users y el servidor decide su URL (por ejemplo, /users/123).
  • Usa PUT cuando ya conoces la URL exacta del recurso que quieres crear o actualizar. Por ejemplo, para actualizar el usuario 123 envías los datos a /users/123.

3.2. Otros métodos útiles

  • HEAD: igual que GET, pero el servidor no devuelve el cuerpo, solo las cabeceras. Sirve para consultar datos de un recurso (tamaño, tipo, fecha de modificación) sin descargarlo. Lo usan mucho las cachés y los rastreadores (crawlers).
  • PATCH: parecido a PUT, pero hace una modificación parcial: solo se envía la parte que cambia. Por ejemplo, para cambiar el correo de un usuario sin enviar su nombre, sus apellidos, etc.
  • OPTIONS: devuelve los métodos que el servidor admite para una URL. También se usa en las peticiones previas (preflight) de CORS, en las que el navegador pregunta al servidor si puede enviar la petición real desde otro origen.

3.3. Métodos de diagnóstico y menos comunes

  • TRACE: permite ver cómo cambia una petición al pasar por los nodos de la red (proxies, pasarelas) antes de llegar al servidor. Se usa para depurar, y casi siempre está desactivado por seguridad.
  • CONNECT: abre un túnel de red. Su uso más común es crear una conexión HTTPS a través de un proxy HTTP.

HTTP/2, a pesar de sus grandes mejoras de rendimiento, no añadió ningún método nuevo: los verbos significan lo mismo.

4. Mensajes HTTP: petición y respuesta

Toda la comunicación en la web es un intercambio de mensajes de texto entre el cliente y el servidor. Conocer su estructura es fundamental.

4.1. Estructura de una petición

Una petición HTTP es un conjunto de líneas que el navegador envía al servidor. Tiene tres partes:

  • Línea de inicio: la primera línea, con tres elementos: el método (GET, POST…), la ruta del recurso y la versión del protocolo (HTTP/1.1).
  • Cabeceras: líneas opcionales con información sobre la petición o el cliente (navegador, sistema operativo…). Cada línea tiene el nombre de la cabecera, dos puntos (:) y su valor.
  • Cuerpo: un bloque de datos opcional, separado de las cabeceras por una línea en blanco. Sirve para enviar datos al servidor, por ejemplo los de un formulario con POST.

Ejemplo de una petición POST para crear un usuario (las líneas con # son comentarios para explicarla; no forman parte del mensaje):

# --- Línea de inicio ---
POST /api/users HTTP/1.1

# --- Cabeceras ---
Host: api.miweb.com
Content-Type: application/json
Content-Length: 64
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)

# --- Línea en blanco (separa las cabeceras del cuerpo) ---

# --- Cuerpo ---
{
  "name": "Juan Pérez",
  "email": "juan.perez@example.com"
}

4.2. Estructura de una respuesta y códigos de estado

La respuesta es el conjunto de líneas que el servidor devuelve al navegador. También tiene tres partes:

  • Línea de estado: la primera línea, con la versión del protocolo, un código de estado que indica el resultado de la petición y un texto con su significado.
  • Cabeceras: líneas opcionales con información sobre la respuesta o el servidor.
  • Cuerpo: el recurso pedido (el HTML de la página, una imagen, datos en JSON…).

Los códigos de estado son números de tres cifras y se agrupan en cinco clases:

Rango Clase Significado
1xx Respuestas informativas La petición se ha recibido y el proceso continúa.
2xx Peticiones correctas La petición se ha recibido, entendido y aceptado. Por ejemplo, 200 OK.
3xx Redirecciones Hay que hacer algo más para completar la petición. Por ejemplo, 301 Moved Permanently.
4xx Errores del cliente La petición está mal escrita o no se puede atender. Por ejemplo, 404 Not Found.
5xx Errores del servidor El servidor ha fallado al atender una petición aparentemente válida. Por ejemplo, 500 Internal Server Error.

Ejemplo de respuesta 201 Created a la petición anterior:

# --- Línea de estado ---
HTTP/1.1 201 Created

# --- Cabeceras ---
Date: Tue, 21 Oct 2025 10:30:00 GMT
Content-Type: application/json
Content-Length: 77
Location: /api/users/123
Server: nginx/1.26.3

# --- Línea en blanco ---

# --- Cuerpo ---
{
  "id": 123,
  "name": "Juan Pérez",
  "email": "juan.perez@example.com"
}

4.3. Cabeceras HTTP

Las cabeceras HTTP son los parámetros que acompañan a una petición o a una respuesta y dan información esencial sobre ella. Tienen la forma Cabecera: valor y las envían automáticamente el navegador o el servidor.

Algunas de las más comunes:

  • Host: el dominio al que va la petición.
  • User-Agent: información sobre el navegador y el sistema operativo del cliente.
  • Accept: los tipos de contenido que entiende el cliente.
  • Content-Type: el tipo MIME del contenido del cuerpo.
  • Content-Length: el tamaño del cuerpo en bytes.
  • Authorization: las credenciales para autenticar al cliente.
  • Server: información sobre el software del servidor que ha generado la respuesta.

5. Tipos MIME

5.1. El problema: más allá del texto plano

HTTP se diseñó al principio para transportar archivos de texto plano (ASCII). Con el tiempo hubo que enviar también otros tipos de archivos (imágenes, vídeos, sonidos, documentos PDF…), y hacía falta una forma de «etiquetarlos» para que el navegador supiera cómo interpretarlos.

Este problema ya había aparecido años antes en el correo electrónico, cuando se quisieron enviar adjuntos que no eran texto plano.

5.2. La solución: MIME

Para resolverlo se crearon los tipos MIME (Multipurpose Internet Mail Extensions), unas especificaciones que nacieron para dar formato a los mensajes de correo que no eran ASCII. Fueron tan útiles que otros protocolos los adoptaron enseguida; el más importante, HTTP.

Un tipo MIME, también llamado «tipo de medio» o «tipo de contenido», indica la naturaleza y el formato de un documento, un archivo o un conjunto de datos. Es como el DNI del archivo: le dice al navegador si lo que recibe es un HTML para mostrar, una imagen, un JSON para procesar con JavaScript o un archivo para descargar.

5.3. La estructura tipo/subtipo

Todo tipo MIME tiene este formato, con dos partes:

tipo/subtipo

# Ejemplo: text/html
# - Tipo: text (es un archivo de texto legible)
# - Subtipo: html (el formato es HyperText Markup Language)
  • Tipo: la categoría general del contenido (text, image, audio, video, application).
  • Subtipo: el formato exacto dentro de esa categoría (html, jpeg, mpeg, mp4, json).

5.4. Tipos MIME habituales

Tipo MIME Descripción Ejemplo de archivo
text/html Documento HTML (HyperText Markup Language). index.html
text/css Hoja de estilos (Cascading Style Sheets). style.css
text/javascript Código JavaScript. Es el tipo oficial desde 2022; antes se usaba application/javascript, que todavía funciona. script.js
application/json Datos en formato JSON (JavaScript Object Notation). data.json
image/jpeg Imagen JPEG. foto.jpg
image/png Imagen PNG (Portable Network Graphics). logo.png
image/svg+xml Imagen vectorial SVG (Scalable Vector Graphics, escrita en XML). icono.svg
application/pdf Documento PDF (Portable Document Format). documento.pdf
multipart/form-data Formato de envío de los formularios HTML que suben archivos. — (es un formato de envío)

5.5. Cómo se usan en la práctica

  1. En la cabecera HTTP Content-Type. Es la forma principal. Cuando el servidor envía una respuesta, incluye esta cabecera para decirle al navegador qué tipo de dato le envía. Del mismo modo, cuando el cliente envía datos (por ejemplo, con POST), la usa para indicar su formato.
  2. En el código HTML. Algunas etiquetas indican el tipo de lo que enlazan:
    • En <link> y <script>: en HTML5 no hace falta indicar el tipo de las hojas de estilo ni de los scripts, porque el navegador ya supone text/css y JavaScript. En <script> solo se pone type en casos especiales, como type="module". 
      <!-- Enlazar una hoja de estilos -->
<link rel="stylesheet" href="/css/style.css">

<!-- Incluir un script (no hace falta type) -->
<script src="/js/main.js"></script>
    • En los formularios que suben archivos: el atributo enctype indica con un tipo MIME cómo se codifican los datos. Para enviar archivos hace falta multipart/form-data. 
      <form action="/upload" method="post" enctype="multipart/form-data">
  <input type="file" name="archivo">
  <button type="submit">Subir archivo</button>
</form>

6. HTTPS: la capa de seguridad de la web

El protocolo seguro de transferencia de hipertexto (Hypertext Transfer Protocol Secure, HTTPS) es un protocolo basado en HTTP para transferir datos de forma segura. Dicho de forma sencilla: es la versión segura de HTTP.

6.1. De SSL a TLS

La web es insegura por naturaleza. Cuando se diseñaron los protocolos en los que se basa (como TCP/IP y el propio HTTP), lo importante era conectar, no la seguridad. Por eso, con HTTP toda la información viaja como texto plano y cualquiera que esté en medio de la comunicación puede interceptarla y leerla (es el ataque de intermediario o man-in-the-middle).

Para resolver este grave problema, en 1994 la empresa Netscape (creadora del primer navegador web comercial) presentó HTTPS. La «S» final significa «seguro» (secure) y se consigue añadiendo una capa de cifrado entre HTTP y TCP. El protocolo original de esa capa se llamaba SSL (Secure Sockets Layer).

Con el tiempo se descubrieron vulnerabilidades en SSL y se sustituyó por un estándar más moderno y seguro, TLS (Transport Layer Security), que hoy va por la versión 1.3. Aunque lo que se usa es TLS, mucha gente sigue diciendo «SSL» por costumbre.

Importante: todas las versiones de SSL están obsoletas y se consideran inseguras. Lo correcto hoy es hablar de TLS, aunque se siga diciendo «certificados SSL».

6.2. Los tres pilares de HTTPS

HTTPS no solo añade «seguridad»: da tres garantías concretas.

  1. Cifrado (confidencialidad): la comunicación entre el cliente y el servidor va cifrada. Si alguien intercepta los datos, solo verá caracteres ilegibles, así que se protegen las contraseñas, los datos personales o las tarjetas de crédito.
  2. Integridad: los datos no se pueden modificar por el camino sin que se note. La información llega exactamente como se envió, en los dos sentidos.
  3. Autenticación: HTTPS comprueba que hablas con el servidor correcto y no con un impostor. Para eso se usan los certificados digitales, que funcionan como el DNI del sitio web.

6.3. De excepción a estándar: cómo lo muestran los navegadores

Tradicionalmente, los navegadores han indicado que la conexión es segura con un icono, normalmente un candado junto a la dirección. Cada navegador lo muestra de una forma un poco distinta.

Lo importante es que la situación ha cambiado. Antes, HTTP era lo normal y HTTPS la excepción; hoy es al revés. Los navegadores modernos, como Chrome, Firefox o Edge, marcan los sitios con HTTP como «No seguro», para animar a que toda la web use HTTPS.

6.4. Funcionamiento: el handshake de TLS

Antes de enviar ningún dato de la página, el cliente (navegador) y el servidor negocian un canal seguro. Este proceso se llama handshake de TLS («apretón de manos»). Es complejo, pero se puede resumir en estos pasos:

  1. El cliente saluda (Client Hello): el navegador contacta con el servidor y le envía las versiones de TLS que admite y la lista de algoritmos de cifrado que puede usar.
  2. El servidor responde (Server Hello): el servidor elige la versión de TLS y el algoritmo más seguro que admitan los dos, y le envía al cliente su certificado digital. El certificado contiene, entre otras cosas, el nombre de dominio del sitio y su clave pública.
  3. El cliente comprueba el certificado: el navegador verifica que no ha caducado, que corresponde al dominio que visita y que lo ha firmado una autoridad de certificación (CA) de confianza (el navegador trae una lista de CA de confianza).
  4. Se genera una clave de sesión: si el certificado es válido, el cliente y el servidor acuerdan una clave simétrica secreta, la que se usará para cifrar todo lo demás. En la forma clásica (TLS 1.2 con RSA), el navegador la genera, la cifra con la clave pública del servidor y se la envía.
  5. El servidor obtiene la clave de sesión: el servidor la descifra con su clave privada, la única que puede descifrar lo cifrado con su clave pública.
  6. Comunicación cifrada: a partir de aquí, el cliente y el servidor tienen la misma clave de sesión. Todas las peticiones y respuestas HTTP se cifran y descifran con ella, y la conexión es segura.

En TLS 1.3, la versión actual, la clave de sesión no viaja nunca, ni siquiera cifrada: el cliente y el servidor intercambian unos datos públicos (con el algoritmo Diffie-Hellman) y cada uno calcula por su cuenta la misma clave. El certificado y la clave privada del servidor sirven para demostrar que el servidor es quien dice ser. Además, el handshake es más corto, como ves en el diagrama.

7. Servidores web: Apache y Nginx

7.1. El ecosistema de un servidor web: el stack

Para poner en marcha un servidor web, lo primero es el sistema operativo sobre el que funcionarán los servicios; casi siempre es Linux. Además hace falta un gestor de bases de datos (como MariaDB o MySQL) y un intérprete para el contenido dinámico (como PHP, Python o Node.js). A este conjunto de tecnologías se le llama stack. Por ejemplo, el stack LAMP es Linux, Apache, MySQL/MariaDB y PHP, y el LEMP cambia Apache por Nginx (que se pronuncia engine-x).

Además de este software, una de las piezas más importantes es el propio servidor web, y aquí aparecen las dudas.

Hay muchos servidores web: Apache y Nginx, los más conocidos y usados, y otros como Microsoft IIS (en servidores Windows), LiteSpeed o Caddy.

No se puede decir que Apache sea mejor que Nginx ni al revés: cada uno tiene sus puntos fuertes y débiles, y encaja mejor en unas situaciones que en otras.

7.2. La diferencia fundamental: cómo atienden las conexiones

Para entender por qué Nginx es famoso por su rendimiento hay que conocer su arquitectura. Nginx se diseñó expresamente para resolver el problema C10K: atender diez mil conexiones de clientes a la vez en un solo servidor.

  • Apache HTTP Server: usa un modelo basado en procesos o hilos, que se elige con un módulo MPM (Multi-Processing Module). En su configuración más clásica (prefork, la que se usa con mod_php) crea un proceso por cada conexión. Esto facilita escribir módulos, pero cada usuario conectado consume bastante memoria RAM y, con muchas conexiones a la vez, el consumo se dispara. Los MPM más modernos (worker y event, el que se usa por defecto si no hay mod_php) usan hilos y aguantan mucho mejor la carga.
  • Nginx: usa una arquitectura asíncrona y dirigida por eventos. En lugar de un proceso por conexión, tiene un proceso maestro que gestiona unos pocos procesos de trabajo (workers). Cada worker atiende miles de conexiones a la vez en un solo hilo, porque no se queda bloqueado esperando a que termine una conexión: reacciona a los eventos (por ejemplo, que llega una petición). Este modelo aprovecha muy bien la CPU y la memoria.

7.3. Evolución y casos de uso

Nginx está pensado para dar más rendimiento y aguantar más tráfico y usuarios que Apache. Al principio destacaba sobre todo sirviendo contenido estático (HTML, CSS, imágenes).

Por eso, al principio se usaba sobre todo para servir archivos estáticos y como balanceador de carga o proxy inverso delante de Apache. En esta configuración híbrida, Nginx recibía todas las peticiones, servía los archivos estáticos a gran velocidad y solo pasaba a Apache las peticiones de contenido dinámico (por ejemplo, PHP), aprovechando lo mejor de los dos.

A medida que la web necesitaba exprimir al máximo la velocidad y la eficiencia, muchos sitios sustituyeron Apache por Nginx del todo, gracias a que Nginx maduró y a herramientas como PHP-FPM, que le permiten gestionar contenido dinámico de forma muy eficiente.

Servicios actuales como Netlify, Vercel, GitHub Pages o Firebase Hosting están especializados en servir sitios estáticos en todo el mundo a gran velocidad, con principios de eficiencia parecidos a los que hicieron famoso a Nginx.

7.4. Comparativa: puntos fuertes y débiles

Característica Apache Nginx
Rendimiento con contenido estático Bueno, pero consume más memoria. Excelente, con muy poco consumo de memoria y CPU.
Rendimiento con contenido dinámico Muy bueno. PHP se integra directamente con mod_php (o con PHP-FPM). Excelente. Necesita un gestor de procesos externo, como PHP-FPM.
Configuración Muy flexible. Permite configurar cada directorio con archivos .htaccess, algo ideal en los hostings compartidos. Más restrictiva. No admite archivos tipo .htaccess: toda la configuración está centralizada, lo que mejora el rendimiento.
Flexibilidad y módulos Muy flexible, con un ecosistema de módulos enorme y maduro para casi cualquier necesidad. También es modular, pero tiene menos módulos, centrados en las funciones clave de un servidor web.

7.5. Varios sitios en un servidor: server blocks

Gracias a la cabecera Host, un mismo servidor con una sola IP puede alojar muchos sitios web. En Apache cada sitio se configura en un virtual host; en Nginx, en un server block: un bloque server { … } que dice qué dominios atiende (server_name) y dónde están sus archivos (root).

En Debian, Nginx guarda la configuración de cada sitio en /etc/nginx/sites-available/ y la activa con un enlace simbólico en /etc/nginx/sites-enabled/. Cuando alguien escribe http://portfolio.com en su navegador, pasa esto:

  1. El navegador envía la petición a la IP de tu servidor.
  2. La petición lleva la cabecera Host: portfolio.com.
  3. Nginx recibe la petición en el puerto 80 y mira la cabecera Host.
  4. Nginx busca, entre los server blocks activos (los de sites-enabled), el que tiene un server_name que coincide con portfolio.com.
  5. Usa la configuración de ese bloque (por ejemplo, root /var/www/portfolio.com/html) para servir el archivo correcto.

Para añadir un segundo sitio a un servidor que ya tiene uno (por ejemplo, portfolio.com junto a disenyo.com):

  1. Prepara los archivos en un directorio nuevo, separado del primer sitio.
  2. Crea un archivo de configuración nuevo en sites-available para el segundo sitio.
  3. Escribe en él un server block nuevo que apunte a los archivos del segundo sitio: cambian las directivas server_name y root.
  4. Actívalo con un enlace simbólico en sites-enabled, como el primero, y recarga Nginx.
