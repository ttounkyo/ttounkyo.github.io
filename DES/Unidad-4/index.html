Unidad 4. Servicio DNS (Domain Name System)

1. Introducción

El sistema de nombres de dominio, DNS (Domain Name System), es el mecanismo que traduce nombres de dominio a direcciones IP. A las personas nos resulta más fácil usar un nombre (de un equipo, de una web, de un servidor de correo…) como www.gva.es que su dirección IP (por ejemplo, 193.144.127.85). El DNS no solo resuelve nombres a direcciones IP: también hace la resolución inversa, es decir, averigua el nombre de dominio a partir de una IP.

El DNS hace que el nombre de dominio sea independiente de la IP: un dominio puede cambiar de IP sin que sus usuarios lo noten. Incluso es habitual que un dominio tenga varias IP, para tener redundancia si se cae un equipo o para repartir la carga. El DNS también sirve para identificar los servidores de correo de un dominio, cada uno de los equipos de la red, los servidores de impresión, etc.

2. Sistemas de nombres planos y jerárquicos

El problema de identificar los equipos existe desde las primeras redes de ordenadores y no es exclusivo de TCP/IP: hacía falta una forma «humana» de nombrarlos.

En los inicios de ARPANET (la red predecesora de Internet), los nombres de los equipos se centralizaban en un archivo llamado HOSTS.TXT (lo que hoy es /etc/hosts en Linux), con el nombre de cada equipo y su IP. Es lo que se llama un sistema de nombres plano. Sirve para redes pequeñas, pero no es escalable ni práctico en redes grandes y mucho menos en Internet.

2.1. Ejemplo de archivo de nombres plano

Un archivo /etc/hosts de una red pequeña podría ser así:

127.0.0.1       localhost
127.0.1.1       hostname
192.168.1.10    servidor
192.168.1.20    pc1

3. Elementos del sistema de nombres de dominio

El espacio de nombres de dominio está formado por todos los nombres válidos para identificar servicios o máquinas en una red. Se representa con una estructura jerárquica en forma de árbol invertido, en la que cada nodo se separa de los demás con un punto.

3.1. Nombres de dominio

Los nombres de dominio están formados por una o más cadenas de caracteres separadas por puntos, llamadas etiquetas (labels), y no distinguen entre mayúsculas y minúsculas. Por ejemplo, www.deaw.es. es lo mismo que WWW.deaw.ES.

3.2. El dominio raíz

En teoría, todos los dominios terminan con un punto (.), porque el árbol de nombres empieza en el dominio ., llamado dominio raíz (root). En realidad es un elemento nulo de 0 caracteres que se representa con un punto.

Un dominio se lee de derecha a izquierda, empezando por el punto, aunque en la práctica lo leemos de izquierda a derecha. El punto final normalmente se omite, porque los programas lo añaden por defecto, pero a veces hay que escribir el nombre completo incluyendo el dominio raíz: es lo que se llama nombre de dominio completo o FQDN (Fully Qualified Domain Name).

3.3. Dominios y subdominios

Como el espacio de nombres es jerárquico, se habla de dominios y subdominios. Por ejemplo, deaw.es. es un subdominio del dominio es. y www.deaw.es. es un subdominio de deaw.es.

Los dominios que cuelgan directamente del dominio raíz se llaman dominios de primer nivel o de nivel superior (TLD, Top Level Domains); los que cuelgan de los TLD son dominios de segundo nivel, y así sucesivamente.

3.4. Zonas

Una zona es una parte del espacio de nombres de dominio cuya administración depende de un único responsable. Los servidores que gestionan la zona tienen toda su información y se dice que son autorizados para esa zona. Las zonas se guardan en archivos de texto o en bases de datos, según el programa con el que se monte el servidor DNS y cómo se configure.

Por ejemplo, esta es una parte del archivo de zona del dominio deaw.es.:

...
deaw.es.       IN NS    ns1.deaw.es.
ns1.deaw.es.   IN A     192.168.1.20
natos.deaw.es. IN A     192.168.1.21
waor.deaw.es.  IN A     192.168.1.22
www.deaw.es.   IN CNAME natos.deaw.es.
ftp.deaw.es.   IN CNAME waor.deaw.es.
...

Cada línea es un registro de recurso (RR, Resource Record). Los RR guardan datos sobre nombres de dominio y direcciones IP, y un archivo de zona es una serie de RR. Por ejemplo, los registros de tipo A asocian un nombre con una dirección IP, los de tipo PTR asocian una IP con un nombre (búsqueda inversa) y los de tipo NS indican un servidor DNS de la zona. El servidor DNS usa estos registros para responder a las consultas sobre su zona.

Cuando un servidor DNS es autorizado para una zona, es el responsable de sus nombres. En el ejemplo, ns1.deaw.es es el servidor autorizado para la zona deaw.es. y en él se definen los nombres que cuelgan de deaw.es, como www.deaw.es, ftp.deaw.es o natos.deaw.es.

Quien administra la zona puede delegar o no algunos de sus subdominios. Supón que de deaw.es. cuelgan teoria.deaw.es. y practicas.deaw.es., y se decide delegar solo practicas.deaw.es.: entonces habrá otro servidor DNS autorizado para practicas.deaw.es., que guardará el archivo de zona de ese dominio.

Una zona no es lo mismo que un dominio. Un dominio es un subárbol del espacio de nombres, y los datos de sus nombres pueden estar guardados en una o varias zonas, repartidas en uno o varios servidores DNS.

En resumen: una zona es una porción de un dominio.

Un servidor DNS puede ser autorizado para varias zonas; por ejemplo, el mismo servidor puede serlo para la zona deaw.es. y para la zona seguridadinformatica.es.

4. Registros de recursos (RR)

Vamos a ver los registros de recursos más utilizados. Antes hay que aclarar algunos conceptos.

4.1. $TTL (Time To Live)

El TTL o tiempo de vida indica, en segundos, durante cuánto tiempo son válidos los RR. También se puede indicar en semanas ($TTL 1W), días ($TTL 7D), horas ($TTL 168H) o minutos ($TTL 10080M).

Dicho de otra forma, el TTL marca cuánto pueden tardar en notarse los cambios que hagas en un RR: los servidores DNS que guarden esos registros en su caché los usarán durante ese tiempo antes de volver a preguntar. Con los ejemplos anteriores, hasta una semana. Se declara al principio del archivo de zona.

4.2. $ORIGIN

La directiva $ORIGIN define el nombre de dominio que se añade al final de cualquier nombre que no acabe en punto (nombres relativos o no cualificados), para convertirlo en un FQDN. Si un nombre acaba en punto, ya es un FQDN y no se le añade nada.

$ORIGIN nombre-dominio

Por ejemplo:

$ORIGIN deaw.es.
; A partir de aquí se añade deaw.es. a todos los nombres relativos

4.3. Formato general de los RR

Los RR se escriben en los archivos de zona con este formato:

Nombre-de-dominio [TTL] Clase Tipo Dato

Por ejemplo:

profesor.deaw.es. 7200 IN A 192.168.10.254

4.4. Registro SOA (Start Of Authority)

Da la información de autoridad de una zona: el servidor de nombres primario, el correo del administrador, el número de serie o versión de la zona y varios temporizadores.

deaw.es. IN SOA ns1.deaw.es. super.deaw.es. (
    2019042501  ; serial
    604800      ; refresh (7 días)
    86400       ; retry (1 día)
    2419200     ; expire (28 días)
    604800 )    ; TTL negativo (7 días)
Campo Qué significa
deaw.es. El nombre del dominio al que pertenece la zona.
IN La clase del registro. IN significa Internet y es la habitual.
SOA El registro de autoridad de la zona, con su información principal de configuración y control.
ns1.deaw.es. El servidor DNS primario (maestro) de la zona: el autorizado principal, desde el que se propagan los cambios.
super.deaw.es. El correo del administrador de la zona. El primer punto sustituye a la @: equivale a super@deaw.es.
2019042501 (serial) El número de versión de la zona. Se aumenta en cada cambio para que los servidores secundarios sepan que tienen que actualizarse. El formato habitual es AAAAMMDDNN: 2019/04/25, revisión 01. Tiene que caber en 32 bits, así que no puede pasar de 10 cifras.
604800 (refresh) Segundos que esperan los servidores secundarios antes de comprobar si hay cambios: 7 días.
86400 (retry) Lo que espera un secundario para volver a intentarlo si no consigue conectar con el primario: 1 día.
2419200 (expire) Tiempo máximo que un secundario puede seguir usando la zona sin contactar con el primario: 28 días. Pasado ese tiempo, la zona deja de considerarse válida.
604800 (TTL negativo) Tiempo que se guardan en caché las respuestas negativas (por ejemplo, cuando un dominio no existe): 7 días.

Ejemplo del TTL negativo: si intentas entrar en esta-web-no-existe-12345.com, el servidor DNS responde con el error NXDOMAIN (Non-Existent Domain).

  • Sin TTL negativo: si 1.000 personas escriben mal tu dominio a la vez, tu servidor DNS recibe 1.000 consultas inútiles sobre algo que no existe.
  • Con TTL negativo: el servidor DNS dice: «Este dominio no existe, y no me vuelvas a preguntar por él durante los próximos 7 días, porque la respuesta será la misma».

4.5. Registro NS (Name Server)

Indica cuáles son los servidores DNS autorizados de un dominio. También se usa cuando se delega la administración de subdominios en otros servidores.

...
deaw.es. IN NS ns1.deaw.es.  ; Servidor DNS maestro
deaw.es. IN NS ns2.deaw.es.  ; Servidor DNS esclavo
deaw.es. IN NS dns.deaw.net. ; Servidor DNS esclavo

ns1.deaw.es. IN A 192.168.10.20
ns2.deaw.es. IN A 192.168.10.21

; DELEGACIÓN
practicas.deaw.es. IN NS ns1.practicas.deaw.es.
redes.deaw.es.     IN NS dns.deaw.net.
Registro Qué significa
deaw.es. IN NS ns1.deaw.es. ns1.deaw.es es un servidor DNS autorizado para deaw.es; aquí, el maestro.
deaw.es. IN NS ns2.deaw.es. ns2.deaw.es es un servidor esclavo del dominio, que da redundancia.
deaw.es. IN NS dns.deaw.net. Un servidor DNS externo (de otro dominio) también autorizado para deaw.es.
ns1.deaw.es. IN A 192.168.10.20
ns2.deaw.es. IN A 192.168.10.21		 Registros A con la dirección IP de cada servidor DNS.
practicas.deaw.es. IN NS ns1.practicas.deaw.es. Delegación del subdominio practicas.deaw.es a su propio servidor DNS. Así otra parte del dominio la gestiona otro servidor.
redes.deaw.es. IN NS dns.deaw.net. Delegación del subdominio redes.deaw.es a un servidor DNS externo.

4.6. Registro A (Address)

También llamado registro de dirección, asocia un nombre de dominio completo (FQDN) con una dirección IPv4. Para las direcciones IPv6 se usa el registro AAAA.

...
ns1.deaw.es.   IN A 192.168.1.20
ns2.deaw.es.   IN A 192.168.1.21
natos.deaw.es. IN A 192.168.1.22
...

4.7. Registro CNAME (Canonical Name)

Crea alias de nombres definidos en registros A. Importante: un CNAME siempre apunta a otro nombre, nunca directamente a una IP.

...
natos.deaw.es. IN A     192.168.1.22
www.deaw.es.   IN CNAME natos.deaw.es.
ftp.deaw.es.   IN CNAME natos.deaw.es.
...

Un CNAME también puede apuntar a un nombre de otro dominio:

...
www.deaw.es. IN CNAME www.google.com.
...

4.8. Registro MX (Mail Exchange)

Define los servidores que reciben el correo del dominio. El número es la prioridad: cuanto menor es el número, mayor es la prioridad. Tienen que apuntar a un nombre (con su registro A), no a una IP.

...
deaw.es. IN MX 10 mail1.deaw.es.
deaw.es. IN MX 20 mail2.deaw.es.

mail1.deaw.es. IN A 192.168.1.100
mail2.deaw.es. IN A 192.168.1.101
...

4.9. Registro PTR (Pointer Record)

Hace la correspondencia inversa: de dirección IP a nombre de dominio. Se usa en las zonas de resolución inversa, por ejemplo para comprobar la identidad de un equipo. Para la red 192.168.1.0/24, con el nombre completo:

...
20.1.168.192.in-addr.arpa. IN PTR ns1.deaw.es.
21.1.168.192.in-addr.arpa. IN PTR ns2.deaw.es.
...

O de forma abreviada, dentro del archivo de la zona inversa:

...
20 IN PTR ns1.deaw.es.
21 IN PTR ns2.deaw.es.
22 IN PTR natos.deaw.es.
...

Cómo se entiende el nombre de un registro de resolución inversa:

  • .arpa (Address and Routing Parameter Area): es un dominio de nivel superior de infraestructura. A diferencia de .com o .es, no es para sitios web, sino para funciones técnicas internas de Internet.
  • in-addr: el subdominio de .arpa que gestiona las direcciones IPv4. Para IPv6 se usa ip6.arpa.
  • ¿Por qué la IP aparece al revés (20.1.168.192)? Porque el DNS lee los nombres de derecha a izquierda, de lo más general a lo más concreto. En una IP, la red es lo más general (192) y el equipo lo más concreto (.20). Al darle la vuelta, el DNS busca primero la red y al final el equipo, con la misma lógica que en un dominio normal.
  • El punto final representa la raíz: indica que el nombre es un FQDN y que el servidor no tiene que añadirle nada.
  • Importancia en el correo electrónico: muchos servidores de correo rechazan los mensajes si la IP de origen no tiene un registro PTR válido. Así comprueban que el servidor que envía es quien dice ser, lo que ayuda a frenar el spam.

4.10. Registro TXT (Text)

Asocia un texto cualquiera a un dominio. Hoy se usa sobre todo para la seguridad del correo (SPF, DKIM) y para demostrar que eres el propietario de un dominio ante otros servicios.

...
@ IN TXT "Descripción: Servidor maestro de la red DEAW"
@ IN TXT "v=spf1 ip4:192.168.1.100 -all"

5. Tipos de servidores DNS

5.1. Servidor maestro o primario

Define una o varias zonas de las que es autorizado. Sus archivos de zona son de lectura y escritura, y es en ellos donde el administrador añade, modifica o elimina nombres de dominio.

  • Si un cliente u otro servidor DNS le pregunta por un nombre de dominio para el que es autorizado, consulta sus archivos de zona y responde.
  • Si le preguntan por un nombre para el que no es autorizado, tendrá que preguntar a otros servidores DNS o responder que no conoce la respuesta.

5.2. Servidor esclavo o secundario

También define una o varias zonas para las que es autorizado. La diferencia es que obtiene los archivos de zona de otro servidor autorizado, normalmente el maestro, mediante una transferencia de zona. Sus archivos de zona son de solo lectura: el administrador no los edita; los cambios se hacen en el maestro, que es quien transfiere la zona.

Responde a los clientes y a otros servidores igual que un maestro. Un servidor puede ser maestro de unas zonas y esclavo de otras a la vez.

Puede haber varios esclavos para una misma zona, para:

  • Reducir y repartir la carga entre varios servidores DNS.
  • Tolerar mejor los fallos.
  • Responder más rápido.

Lo ideal es que los servidores DNS de una misma zona estén en redes y lugares distintos, para que un problema no les afecte a la vez y deje sin resolución los nombres de esa zona.

5.3. Servidor caché

Los servidores DNS se configuran como caché para responder antes, reducir la carga de los equipos y el tráfico de red.

Cuando un servidor DNS recibe una pregunta sobre un dominio para el que no es autorizado, puede preguntar a otros servidores, si está configurado para ello. Si actúa como caché, guarda durante un tiempo (el TTL) las respuestas que ha obtenido. Cada vez que le hacen una pregunta, mira primero si tiene la respuesta en su caché; si la tiene, no necesita preguntar a nadie.

Un servidor DNS es solo caché (cache only) cuando:

  • No es autorizado para ninguna zona.
  • Pregunta a otros servidores DNS para resolver las consultas de los clientes y guarda las respuestas en su caché.

5.4. Servidor reenviador (forwarder)

Cuando a un servidor DNS le preguntan por un nombre del que no tiene información (no es autorizado), puede preguntar a otros servidores. Simplificando, hay dos formas de hacerlo:

  • El servidor resuelve la consulta preguntando él mismo a varios servidores DNS, empezando por los servidores raíz: consulta iterativa.
  • El servidor reenvía la consulta a otro servidor DNS, el reenviador (forwarder), para que la resuelva él: consulta recursiva.

Por tanto, un reenviador es un servidor DNS al que otros servidores DNS envían sus consultas. Se usan para reducir las consultas y el tráfico DNS de una red hacia Internet, y permiten a los equipos locales aprovechar su caché para responder antes.

5.5. Servidor solo autorizado

Un servidor solo autorizado (authoritative only) es autorizado para una o varias zonas, como maestro o esclavo, y no responde a preguntas que no sean de sus zonas. Es decir, no tiene activada la recursividad, no es reenviador y no hace de caché.

5.6. Servidores raíz

En Internet hay un conjunto de servidores DNS autorizados para el dominio raíz .: los servidores raíz (root servers). Tienen el archivo de la zona ., con la información de los servidores DNS autorizados para cada dominio TLD.

Son una parte fundamental de Internet: son el primer paso para traducir los nombres de los equipos a direcciones IP. Todos los servidores DNS que respondan a preguntas sobre nombres para los que no son autorizados tienen que conocerlos.

Hay 13 servidores raíz, y cada uno tiene muchas copias repartidas por todo el mundo: físicamente no son solo 13 equipos. Todas las copias de un mismo servidor raíz comparten la misma IP; cuando un cliente pregunta a esa IP, los routers de Internet llevan la pregunta a la copia más cercana mediante un procedimiento llamado anycast.

Sus nombres tienen la forma letra.root-servers.net, con letras de la A a la M:

5.7. DNS de horizonte dividido (split-horizon)

Es una configuración en la que un mismo servidor DNS da respuestas distintas según quién pregunte (según la IP del cliente). Por ejemplo:

  • Si un empleado pregunta desde la red interna de la empresa, el DNS le da la IP privada del servidor.
  • Si alguien pregunta desde Internet, el DNS le da la IP pública del mismo servidor.

5.8. Maestro oculto (stealth master)

Es un servidor maestro que tiene la zona original pero no aparece en los registros NS del dominio: el público no sabe que existe. Solo los servidores esclavos lo conocen, para poder copiar la zona. Añade una capa de seguridad, porque los atacantes no saben qué servidor es el que permite modificar los datos.

6. Tipos de consultas: recursivas e iterativas

6.1. Consultas recursivas

En una consulta recursiva, el servidor DNS da una respuesta completa. Puede ser de tres tipos:

  • Positiva: devuelve la información del dominio consultado.
  • Negativa: no se puede resolver el nombre de dominio.
  • Error: por un fallo en la red.

6.2. Consultas iterativas

En una consulta iterativa, el servidor DNS puede dar una respuesta parcial. Hay cuatro respuestas posibles:

  • Positiva: devuelve la información del dominio consultado.
  • Negativa: no se puede resolver el nombre de dominio.
  • Referencia: el servidor indica otros servidores a los que se puede preguntar.
  • Error: por un fallo en la red.

7. Resolución inversa

La resolución inversa consiste en obtener el nombre de dominio preguntando por la dirección IP, en lugar de preguntar por el nombre como hemos visto hasta ahora.

7.1. El dominio arpa

La resolución de direcciones IP funciona igual que la de nombres de dominio. Las direcciones IP se tratan como nombres que cuelgan del dominio in-addr.arpa (IPv4) o del dominio ip6.arpa (IPv6).

Cuando haces una pregunta DNS inversa sobre la IP 192.168.1.21, en realidad estás preguntando por el nombre 21.1.168.192.in-addr.arpa. La jerarquía de la IP, tratada como nombre de dominio, va de derecha a izquierda, empezando por in-addr.arpa.

.arpa (Address and Routing Parameter Area) es un dominio de nivel superior que solo se usa para la infraestructura de Internet. Sus subdominios in-addr.arpa e ip6.arpa los usan los servidores DNS para la resolución inversa de direcciones IPv4 e IPv6.

Mapear una dirección IP es asociarla a un nombre del dominio .arpa: la dirección 192.168.1.21 se mapea al nombre 21.1.168.192.in-addr.arpa.

7.2. Zonas de resolución inversa

Los servidores DNS guardan zonas de resolución inversa con registros que asocian direcciones IP con nombres de dominio. Pueden ser maestras (primarias) o esclavas (secundarias).

Las zonas de resolución directa e inversa son independientes, y es responsabilidad de los administradores que su información sea coherente. Además, quien administra la zona directa de un dominio no tiene por qué administrar la zona inversa de sus direcciones IP.

Archivo de zona de resolución directa del dominio deaw.es.:

...
deaw.es.       IN NS    ns1.deaw.es.
ns1.deaw.es.   IN A     192.168.1.20
natos.deaw.es. IN A     192.168.1.21
waor.deaw.es.  IN A     192.168.1.22
altea.deaw.es. IN A     192.168.1.23
www.deaw.es.   IN CNAME natos.deaw.es.
ftp.deaw.es.   IN CNAME waor.deaw.es.
...

Archivo de zona de resolución inversa 1.168.192.in-addr.arpa, que responde a las consultas inversas sobre las IP de la red 192.168.1.0/24:

...
1.168.192.in-addr.arpa.    IN NS  ns1.deaw.es.
20.1.168.192.in-addr.arpa. IN PTR ns1.deaw.es.
21.1.168.192.in-addr.arpa. IN PTR natos.deaw.es.
22.1.168.192.in-addr.arpa. IN PTR waor.deaw.es.
23.1.168.192.in-addr.arpa. IN PTR altea.deaw.es.
...

7.3. Proceso de resolución

La resolución inversa funciona igual que la directa: las direcciones IP se tratan como nombres de dominio, así que también hay consultas recursivas e iterativas, caché, TTL…

Por ejemplo, si un cliente hace una consulta recursiva de la IP 192.168.1.21 a un servidor DNS y este no la tiene en caché, el servidor hará consultas iterativas a los servidores raíz, a los autorizados para 192.in-addr.arpa, y así sucesivamente.

8. Herramientas de diagnóstico

Estas herramientas sirven para consultar servidores DNS y comprobar que resuelven bien. Las capturas están hechas en un servidor Debian (en AWS) consultando el dominio cisco.com; si repites las consultas, las IP, los TTL y los tiempos pueden salir distintos.

8.1. nslookup

Es un programa para consultar servidores DNS. Sirve para saber si un servidor DNS resuelve bien los nombres y las direcciones IP, y para diagnosticar problemas de configuración, frecuentes u ocasionales, de los servidores DNS.

Con nslookup obtienes la IP de un nombre y viceversa, y puedes pedir a los servidores de nombres información sobre los registros (RR) de las zonas de las que son autorizados.

Tiene dos modos: interactivo y no interactivo. El interactivo permite hacer varias consultas seguidas sobre distintos equipos y dominios; el no interactivo muestra solo la información pedida para un nombre.

Funciona en UNIX/Linux y en Windows. En su momento se consideró obsoleto (deprecated), pero hoy se sigue usando con normalidad.

Análisis de nslookup cisco.com

  • Servidor local (Server: 127.0.0.53): el servidor DNS que ha usado tu equipo. 127.0.0.53 es el resolvedor local de los Linux modernos (systemd-resolved). El #53 indica que la consulta se hizo por el puerto 53, el estándar del DNS.
  • Respuesta no autoritativa (Non-authoritative answer): un concepto clave. El servidor que te ha respondido (el local) no es el dueño de los registros de Cisco: los ha sacado de su caché o se los ha preguntado a otros servidores. Es una respuesta «de segunda mano».
  • Dirección IPv4 (Address: 72.163.4.185): la IPv4 del dominio; es el resultado del registro A.
  • Dirección IPv6 (Address: 2001:420:1101:1::185): la IPv6 del dominio; es el resultado del registro AAAA.

Análisis de nslookup -type=ns cisco.com

  • El parámetro -type=ns: le dice a nslookup que no busque la IP del dominio, sino sus servidores de nombres (name servers): los que tienen autoridad para responder por cualquier registro de cisco.com.
  • Servidor (127.0.0.53#53): igual que antes, se usa el resolvedor local de Linux (systemd-resolved) en el puerto 53.
  • Respuesta no autoritativa: el servidor local ha sacado la lista de su caché (de consultas anteriores) en lugar de preguntar en ese momento a los servidores autorizados.
  • Lista de servidores de nombres: salen los 5 servidores autorizados de Cisco, una mezcla de servidores propios (ns1, ns2 y ns3.cisco.com) y de Akamai (akam.net). Así el DNS es rápido y resiste ataques o caídas.
  • Authoritative answers can be found from: esta sección (vacía en la captura) indicaría dónde obtener una respuesta «oficial» y no de caché: en cualquiera de los servidores de la lista.

Análisis de nslookup en modo interactivo

  • Modo interactivo: al ejecutar nslookup sin argumentos entras en un subentorno (con el símbolo >), donde puedes hacer varias consultas seguidas o cambiar opciones sin volver a escribir el comando.
  • set type=ns: define qué tipo de registro buscas; aquí, los servidores de nombres. Otros valores habituales son set type=mx (correo) o set type=a (direcciones IP).
  • Consulta cisco.com: con el tipo ya configurado, basta con escribir el dominio. Se usa el servidor local (127.0.0.53).
  • Interpretación: de nuevo es una respuesta no autoritativa: los datos vienen de la caché del resolvedor local, no directamente de los servidores de Cisco.
  • Servidores encontrados: salen los mismos 5 servidores que con -type=ns, lo que confirma que la información DNS es la misma con una herramienta u otra.

8.2. dig (Domain Information Groper)

Es la herramienta de referencia de administradores de sistemas y profesionales de redes para diagnosticar y consultar servidores DNS. A diferencia de otras, ofrece una visión detallada y técnica de las respuestas del servidor.

  • Estándar profesional: se considera el sucesor de herramientas clásicas como nslookup por su precisión y claridad.
  • Información completa: muestra la cabecera, las banderas de estado (flags), las secciones de autoridad y los tiempos de respuesta.
  • Versátil: se usa sobre todo en la línea de comandos, pero también puede trabajar por lotes, leyendo muchas consultas de un archivo de texto.
  • Multiplataforma: es de UNIX/Linux, pero también está disponible en Windows.

La gran ventaja de dig es que muestra la respuesta del servidor DNS tal como llega, sin procesarla ni simplificarla, lo que facilita encontrar errores de configuración.

Análisis de dig cisco.com a

  • Cabecera (HEADER) y estado: status: NOERROR indica que la consulta ha ido bien. Las flags dan información clave: qr (Query Response): es una respuesta; rd (Recursion Desired): pedimos al servidor que buscara por nosotros; ra (Recursion Available): el servidor admite consultas recursivas. Como no aparece la flag aa (Authoritative Answer), la respuesta no es autoritativa.
  • Sección de pregunta (QUESTION SECTION): ;cisco.com. IN A es lo que le hemos preguntado al servidor: el registro de clase Internet (IN) y tipo A de cisco.com.
  • Sección de respuesta (ANSWER SECTION): cisco.com. 300 IN A 72.163.4.185 es el resultado. El 300 es el TTL en segundos: la respuesta se guardará en caché 5 minutos antes de volver a preguntar a los servidores autorizados.
  • Estadísticas: Query time es lo que tardó la respuesta (aquí, 0 ms, porque ya estaba en la caché); SERVER: 127.0.0.53#53 indica que respondió el resolvedor local, y WHEN, la fecha y hora exactas de la consulta.

Análisis de dig cisco.com mx

  • Registro MX: el parámetro mx pide los servidores de correo del dominio, los que reciben los mensajes enviados a @cisco.com.
  • Sección de respuesta: salen 3 servidores de correo con la estructura [dominio] [TTL] [clase] [tipo] [prioridad] [servidor]. alln-mx-01 tiene la prioridad 10 (es el principal); los de prioridad 20 y 30 son de respaldo.
  • El TTL (1201): en una respuesta que viene de la caché, el TTL va bajando como una cuenta atrás: indica cuántos segundos le quedan a esa información antes de caducar (aquí, unos 20 minutos). Cuando llegue a cero, el resolvedor tendrá que volver a preguntar.
  • Query time: 0 msec: la respuesta ha sido instantánea porque ya estaba guardada en la memoria del resolvedor local (127.0.0.53); no ha hecho falta salir a Internet.
  • flags: qr rd ra: otra vez falta la flag aa: la información es correcta, pero nos la da «de segunda mano» desde la caché.

8.3. host

host es una herramienta de línea de comandos sencilla para hacer consultas DNS: traduce nombres a direcciones IP y viceversa. También sirve para consultar los registros de las zonas, probar el servidor DNS y la conexión a Internet, comprobar listas negras de correo no deseado, diagnosticar problemas del servidor DNS…

Análisis de host cisco.com

  • Registro A (cisco.com has address 72.163.4.185): la dirección IPv4 del servidor web, la que usa el navegador para cargar la página.
  • Registro AAAA (cisco.com has IPv6 address 2001:420:1101:1::185): lo mismo para IPv6. Las grandes empresas ofrecen las dos para asegurar la conectividad.
  • Registros MX (mail is handled by 10 alln-mx-01.cisco.com…): los servidores que reciben el correo enviado a @cisco.com.
  • Prioridad del correo: los números 10, 20 y 30 marcan el orden de preferencia. El de número más bajo (10: alln-mx-01) es el principal; si falla, el correo va al siguiente (20), y así sucesivamente.
  • Redundancia: tener varios registros MX y varias direcciones demuestra que el dominio está preparado para la alta disponibilidad: si cae un centro de datos, los demás siguen dando servicio.

Análisis de la resolución inversa: host 72.163.4.185

  • Consulta inversa automática: si a host le das una IP, entiende que quieres el camino contrario: el nombre asociado a esa dirección (reverse DNS lookup).
  • 185.4.163.72.in-addr.arpa.: el sistema ha invertido la IP 72.163.4.185 y le ha añadido .in-addr.arpa. para buscarla en la jerarquía DNS.
  • domain name pointer: ha encontrado un «puntero de nombre de dominio», es decir, un registro PTR, que une esa IP con un nombre.
  • Resultado: redirect-ns.cisco.com. es el nombre (FQDN) configurado para esa IP. Es habitual que las grandes empresas usen nombres técnicos así para sus IP de infraestructura.
  • ¿Para qué sirve? Para comprobar la identidad: si un servidor dice ser de Cisco pero su resolución inversa apunta a un dominio desconocido o sospechoso, otros servidores podrían bloquearlo o marcar su correo como spam.

Análisis de host -t NS cisco.com

  • El parámetro -t NS: filtra la búsqueda para mostrar solo los registros de servidor de nombres, los que definen qué servidores DNS son autorizados para cisco.com.
  • Servidores propios (ns1, ns2 y ns3.cisco.com): Cisco usa sus propios servidores DNS. Al tener varios, si uno falla los demás siguen respondiendo (redundancia).
  • Servidores externos (akam.net): Cisco también delega en Akamai, una de las mayores redes de distribución de contenido (CDN) del mundo, para que las consultas se respondan rápido desde cualquier parte del planeta.
  • ¿Por qué 5 servidores? Por tolerancia a fallos: para dejar sin DNS a Cisco, un atacante tendría que tumbar a la vez sus servidores y los de Akamai, algo muy difícil.
  • El proceso de resolución: cuando alguien busca www.cisco.com, los servidores raíz y los del TLD .com le dicen: «Yo no sé la IP, pero pregunta a cualquiera de estos 5 servidores: ellos tienen la respuesta oficial».

8.4. whois

No es una herramienta de diagnóstico DNS, pero da información sobre el registro de un dominio.

whois es un protocolo para consultar bases de datos con información del usuario, empresa u organización que ha registrado un nombre de dominio o una dirección IP en Internet. Funciona sobre TCP y solo define cómo se intercambian las preguntas y las respuestas, no el formato de los datos. Por eso los resultados pueden variar según la base de datos whois a la que se pregunte.
